版本：v1.1　最後更新：2026-07-30

## 版本紀錄

| 版本 | 日期 | 修改摘要 |
|---|---|---|
| v1.0 | – | 初版規格 |
| v1.1 | 2026-07-30 | 統一章節編號；補充資料來源與取得方式；新增回測方法論（過度配適、未來函數、交易成本）章節；補充維運排程與通知機制建議；風險章節新增資料／模型相關風險；新增基本假設與範圍邊界 |

## 1. 專案目標

建立一套以「條件機率」為核心的台股分析與訊號系統，具備：

- 可解釋的訊號邏輯
- 可回測、可驗證的規則與模型
- 分階段擴充能力（短期 → 中期 → 長期）
- 明確的風險控管與失效條件

**核心定位：** AI 負責快速分析與訊號產生；人負責最終決策與風險承擔。

**非目標（初期不做）：**
- 全自動無人下單
- 保證獲利
- 高頻交易

## 2. 系統範圍

### 2.1 分析標的
- 大盤：加權指數（TAIEX）
- 權值觀察：台積電（2330）等
- 後續可擴充：電子、金融、個股池

### 2.2 訊號類型
- 方向訊號：偏多 / 偏空 / 中性
- 事件訊號：突破、跌破、量價異常、籌碼轉向
- 風險警示：急跌、波動放大、關鍵支撐失守

### 2.3 時間框架
- 短線：1–5 個交易日
- 波段：1–4 週
- 中期：1–3 個月（後期擴充）

### 2.4 基本假設與範圍邊界（新增）
- 標的限現股，不含期貨、選擇權；融資融券資料（第二階段導入）僅作籌碼面參考指標，不用於產生槓桿部位建議
- 所有訊號皆須經人工確認才可能轉化為下單行為，系統本身不與下單介面連接；第三階段所稱「半自動」仍以人工確認為前提
- 以個人／小規模自用為前提；若未來考慮對外提供訊號或收費，需另外評估是否涉及《證券投資信託及顧問法》中「證券投資顧問業務」的規範邊界（見第 6 節）

## 3. 開發階段規劃

三階段循序漸進，原則上需先達成前一階段驗收標準，才投入下一階段的資源：

| 階段 | 期間 | 核心目標 | 關鍵產出 |
|---|---|---|---|
| 3.1 短期 | 0–2 個月 | 可運行的規則型訊號原型 | 資料管線、10–20 個條件、5–10 條規則、回測報告 |
| 3.2 中期 | 2–6 個月 | 訊號品質提升、風險模組、使用介面 | 評分機制、風險模組、儀表板、績效追蹤 |
| 3.3 長期 | 6–12 個月以上 | 系統化、可擴充、接近實戰輔助 | 個股池訊號、多時間框架、模型監控 |

### 3.1 第一階段：短期（0–2 個月）

**目標：** 可運行的規則型訊號原型

#### 3.1.1 交付成果
- 資料自動更新流程
- 10–20 個可解釋條件（Feature）
- 5–10 條核心訊號規則
- 基礎回測報告
- 每日／盤後訊號輸出（文字或簡單儀表板）

#### 3.1.2 功能需求
- 資料擷取與清洗
- 特徵計算
- 規則引擎（if-then 條件組合）
- 歷史回測（勝率、平均報酬、最大回撤）
- 訊號輸出與紀錄
- 資料管線健康檢查與異常告警（新增：抓取失敗、筆數異常時應主動通知，而非靜默失敗）

#### 3.1.3 資料需求與來源（最低可行）（擴充）

| 資料項目 | 建議來源 | 更新頻率 | 備註 |
|---|---|---|---|
| 加權指數 OHLCV | TWSE OpenAPI（openapi.twse.com.tw）／證交所網站資料 | 每日 | 官方免費資料 |
| 個股（如台積電）OHLCV | TWSE OpenAPI | 每日 | 需自行處理除權息還原 |
| 三大法人買賣超 | TWSE OpenAPI | 每日，盤後公布 | 訊號須使用 T+1 資料，避免未來函數（見 3.1.7） |
| 融資融券、借券 | TWSE／TPEx OpenAPI | 每日 | 第二階段導入 |
| 技術指標（MA、量能均線等） | 內部計算 | 每日 | 基於上述 OHLCV 自行計算，不依賴第三方指標 API |
| （可選）費半、美股期貨代理指標 | 公開行情源 | 每日 | 僅作輔助參考，非核心依賴 |

> 這批資料需求與既有的台股 5 年報酬分析（除權息還原邏輯、大規模資料抓取流程）高度重疊，建議直接沿用既有管線，避免重工。

#### 3.1.4 核心邏輯（短期版）

採用「規則 + 統計驗證」：

**條件示例**
- 指數是否站上／跌破月線、季線
- 外資近 3／5 日淨買賣超方向與金額級距
- 量能是否大於 5 日均量一定倍數
- 台積電相對大盤強弱
- 漲跌家數或市場廣度

**規則示例**
- 偏空：跌破季線 + 外資連續賣超 + 量能放大
- 偏多：站回關鍵均線 + 量能配合 + 權值止穩
- 中性：條件衝突或強度不足

每條規則必須附：
- 明確觸發條件
- 歷史統計結果
- 失效條件

> 上述條件與規則的具體參數（均量倍數門檻、法人買賣超金額級距等）應由回測結果決定，不宜預先寫死；規則定案前須通過 3.1.7 的方法論檢核。

#### 3.1.5 技術建議
- 語言：Python
- 資料處理：pandas / numpy
- 儲存：SQLite 或 PostgreSQL
- 排程：每日收盤後執行，建議以 cron 或 systemd timer 等輕量方式即可，此階段不需要 Airflow 之類的重型排程工具
- 輸出：CSV / Markdown / 簡單 Web 頁面
- 通知：建議用 Telegram Bot API（免費、訊息量無上限）或 Discord Webhook，作為每日訊號推播管道

#### 3.1.6 驗收標準
- 規則可完整回測至少 3–5 年資料，且涵蓋多／空／盤整等不同市場狀態
- 每條規則有統計報告
- 訊號可每日自動產出，並訂出明確的準時率與資料完整率目標
- 邏輯可人工解釋

#### 3.1.7 回測方法論注意事項（新增）

規則型訊號最容易出現「回測好看、實際不可靠」的狀況，建議在開發流程中明確納入以下檢核：

- **避免未來函數（look-ahead bias）：** 法人買賣超等資料為盤後公布，訊號邏輯需確保使用的是「產出當下已公開」的資料（例如以 T-1 已公布的法人資料產生 T 日訊號），避免誤用到當天收盤後才會知道的數字。
- **樣本外驗證（out-of-sample）：** 建議將歷史資料切分為「規則設計期」與「樣本外測試期」，參數只在設計期調整，樣本外資料僅用於驗證，不回頭微調。
- **留意資料窺探／多重檢定（data snooping）：** 同時測試多組條件與規則時，部分規則可能只是「測試次數夠多」而剛好在歷史資料上表現良好。建議記錄測試過的規則總數，對表現顯著性採保守解讀。
- **交易成本與稅負須計入回測：** 台股證交稅一般稅率為成交金額 0.3%（賣方負擔），現股當沖減半為 0.15%，優惠稅率延長至 2027 年底，另有券商手續費（買賣雙邊，牌告費率約 0.1425%，多數券商有折扣）。若回測未計入成本，勝率與報酬會被高估；建議將交易成本設計為可調參數（稅率與優惠期限如有變動，上線前請複核最新公告）。
- **存活者偏誤（survivorship bias）：** 第三階段擴充個股池時，若只用「目前仍上市」的股票做歷史回測，會排除下市／併購個股而使結果偏樂觀，屆時資料來源需能涵蓋歷史上曾經存在的標的。
- **回測期間須涵蓋多種市場狀態：** 建議選取的 3–5 年區間至少包含一次明顯的多頭、空頭與盤整期，才能驗證「分市場狀態運作」（見 3.2.2）的假設是否成立。

### 3.2 第二階段：中期（2–6 個月）

**目標：** 訊號品質提升 + 風險模組 + 使用介面

#### 3.2.1 交付成果
- 特徵擴充（籌碼、波動、相對強度、市場廣度）
- 訊號評分機制（強度 1–5 或機率化）
- 風險控管模組（波動、回撤、部位建議框架）
- 基礎儀表板（盤後總覽）— 建議直接擴充既有的市場資料儀表板（Flask 後端＋前端），加入訊號與規則觸發狀態頁籤，不另起一套介面
- 訊號績效追蹤系統

#### 3.2.2 新增功能

**多因子評分**
不再只輸出「多／空」，而是綜合分數與信心水準。

**四燈號健診系統（新增 v1.1）**
將多因子評分視覺化為四面向燈號，每面向權重 25/100，合計 100 分：

| 面向 | 子項 | 權重 | 燈號門檻（🟢 / 🟡 / 🔴） | 數據來源 |
|---|---|---|---|---|
| 基本面 | EPS 年增率 | 40% | >+5% / ±5% / <-5% | 財報（季/年） |
| | 月營收年增率 | 30% | >+5% / ±5% / <-5% | 公開資訊觀測站 |
| | 毛利率年增差 | 30% | >+2pp / ±2pp / <-2pp | 財報（季/年） |
| 籌碼面 | 外資近5日佔20日均量 | 40% | >+10% / ±10% / <-10% | TWSE三大法人買賣超 |
| | 投信近5日佔20日均量 | 30% | >+5% / ±5% / <-5% | TWSE三大法人買賣超 |
| | 券資比 | 30% | <5% / 5%~15% / >15% | TWSE融資融券 |
| 技術面 | 均線排列 | 40% | MA5>MA20>MA60 / 整理中 / 空頭排列 | OHLCV 內部計算 |
| | RSI (14) | 30% | 50~70 / 30~50或70~80 / <30或>80 | OHLCV 內部計算 |
| | 布林通道位置 | 30% | 中軌之上未觸上軌 / 中軌之下 / 觸及上軌或跌破下軌 | OHLCV 內部計算 |
| 估值面 | 本益比河流位置 | 40% | 偏低 / 合理 / 偏高 | 股價/EPS（財報+行情） |
| | 股價淨值比河流位置 | 30% | 偏低 / 合理 / 偏高 | 股價/每股淨值（財報+行情） |
| | 目前殖利率 | 30% | >5% / 2%~5% / <2% | 股利/股價（公開資訊） |

綜合評分計算方式：
```
綜合成績 = 基本分 × 25% + 籌碼分 × 25% + 技術分 × 25% + 估值分 × 25%
```

| 綜合總分 | 燈號 | 意義 |
|---|---|---|
| ≥ 80 | 🟢 | 強勁 — 全面正向 |
| 60–79 | 🟢🔴 | 偏多 — 多數正向，少數需留意 |
| 40–59 | 🟡 | 中性 — 多空交錯 |
| 20–39 | 🔴🟢 | 偏空 — 多數偏弱 |
| < 20 | 🔴 | 弱勢 — 全面偏弱 |

**分市場狀態運作**
區分多頭、空頭、震盪市，套用不同規則權重。

**風險模組**
- 近期波動率
- 最大回撤監控
- 訊號衝突警示
- 建議觀察停損區（非自動下單）

**績效追蹤**
- 訊號出現後 1／3／5 日表現
- 勝率、盈虧比、連續虧損次數
- 依市場狀態分類統計

**簡單模型輔助（可選）**
邏輯回歸或隨機森林，用於輔助規則評分，必須保持可解釋性，避免純黑盒。

#### 3.2.3 資料擴充
- 融資融券、借券
- 類股指數
- 更多權值股
- 選擇性加入國際代理變數（費半、美股期貨等）

#### 3.2.4 驗收標準
- 訊號有強度分數
- 可依市場狀態切換邏輯
- 有完整績效追蹤報表
- 風險警示可正常運作

### 3.3 第三階段：長期（6–12 個月以上）

**目標：** 系統化、可擴充、接近實戰輔助

#### 3.3.1 交付成果
- 個股池訊號（精選觀察清單）
- 多時間框架整合（日線 + 週線概念）
- 更完整的研究平台（回測、模擬、報告）
- 可選：半自動提醒或券商 API 串接（人工確認後執行）
- 模型監控與衰退偵測

#### 3.3.2 進階能力

**個股層訊號**
在大盤傾向下，篩選相對強弱個股或族群。

**結構變化偵測**
監控規則／模型是否失效（績效衰退、分布偏移）。可考慮的具體方式：規則觸發頻率是否明顯偏離歷史分布、滾動勝率／報酬是否持續低於回測基準、特徵分布是否隨時間出現明顯位移。

**研究與實戰分離**
- 研究環境：自由回測與實驗
- 實戰環境：僅使用通過驗證的穩定規則

**合規與操作邊界**
- 明確「僅輔助、不自動下單」或「半自動需人工確認」
- 操作日誌與責任紀錄

#### 3.3.3 長期架構方向
- 資料層：穩定行情與籌碼資料倉儲
- 特徵層：可版本化的 Feature Store
- 訊號層：規則引擎 + 可選模型
- 評估層：持續回測與線上績效監控
- 應用層：儀表板、警示、報告

#### 3.3.4 驗收標準
- 系統可穩定每日運行
- 有模型／規則衰退監控
- 具備可審計的訊號與決策紀錄
- 擴充新標的或新規則成本可控

## 4. 系統架構（建議）

```
[資料來源：TWSE／TPEx OpenAPI 等]
        ↓
[資料擷取與清洗] ──→ [資料完整性檢查／異常告警]
        ↓
[特徵計算]
        ↓
[規則引擎／模型推論]
        ↓
[訊號與風險評估]
        ↓
[輸出：報告／儀表板／Telegram·Discord 通知]
        ↓
[績效追蹤與回測]
```

原則：
- 每層可獨立測試
- 規則與模型可版本管理
- 所有訊號可回溯原因
- 資料管線本身的健康狀態（準時率、完整率）應與訊號品質分開監控

## 5. 評估指標

**訊號品質**
- 勝率（依持有天期）
- 平均報酬
- 盈虧比
- 最大回撤
- 連續虧損次數
- 不同市場狀態下的穩定性
- （可選）風險調整後報酬指標，供跨規則比較

**系統品質**
- 資料完整率
- 任務成功率
- 訊號產出準時率
- 規則可解釋比例

## 6. 風險與限制（必須寫入規格）

- 歷史有效 ≠ 未來有效
- 台股受外資與國際科技股影響大，結構可能改變
- 資料品質與延遲會影響訊號
- 系統不保證獲利
- 最終下單與風險承擔由使用者負責
- **（新增）過度配適風險：** 規則調參過程可能對歷史資料過度配適，樣本外表現可能明顯低於設計期（對應 3.1.7 方法論）
- **（新增）資料供應商風險：** 免費／官方 API 仍可能變更格式或中斷服務，管線應對來源異常有基本容錯與告警機制
- **（新增）法規邊界：** 若未來考慮將訊號提供給他人使用或收費，需留意《證券投資信託及顧問法》對「證券投資顧問業務」的規範；目前定位為個人使用工具，不涉及此限制

## 7. 開發優先順序（執行清單）

**短期立即做**
1. 定義大盤訊號目標與時間框架
2. 建立資料管線（指數 + 法人 + 基本技術）
3. 設計第一批可解釋條件與規則
4. 完成回測框架（含樣本外驗證與交易成本模型）
5. 每日盤後訊號輸出

**中期**

6. 加入評分與市場狀態切分
7. 建立績效追蹤
8. 加入風險警示
9. 擴充儀表板

**長期**

10. 擴充個股／族群
11. 結構衰退監控
12. 研究與實戰環境分離
13. 視需求考慮半自動化

## 8. 成功定義

系統成功，不代表「會賺錢」，而代表：

- 訊號邏輯清楚、可解釋
- 每條規則都有數據驗證
- 失效時能被發現
- 使用者能據此做更有紀律的決策

以上定義應對應第 5 節的量化指標，作為每個階段是否達標的具體判斷依據。
