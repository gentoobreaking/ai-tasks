## 三、程式設計邏輯問題（依嚴重度排序）

### 🔴 P0：自動開發引擎會 commit 未驗證程式碼（信任鏈斷裂）

`auto_develop.py process_task()` 流程：
```
模型生成 diff → apply_diff() → run_tests() → git_commit() → status=done
```

問題：
1. `run_tests()` 中 `pytest` rc=5（無測試）**被當作通過** → 「測試通過」是假象
2. `pyright` include 路徑錯誤 → 永遠掃 0 個檔案 → 型別檢查也是假象
3. ruff 333 errors → 若嚴格執行，任務永遠失敗；現狀是 `run_tests` 檢查 `ruff check .` 會失敗 → 任務全部 blocked（T006/T008 就是這樣死的）
4. **測試失敗時沒有任何自動修復**（code 內有 `# TODO: 這裡可以加入自動修復迴圈`）→ 直接 `_record_failure`

**風險**：任務被標記 `done` 但程式碼可能完全沒被驗證過；或反過來，品質閘門太嚴導致所有任務 blocked。

**建議**：
- 品質閘門改分層：`ruff` 只檢查**新增/修改檔案**（`git diff --name-only` + `ruff check <files>`），不檢查全專案歷史債
- 測試失敗時加**自動修復迴圈**（把測試錯誤餵回模型，最多 2 輪），修不好才標 blocked
- `pytest` rc=5 時明確印出「無測試」警告，不要默默當通過

### 🟠 P1：模型與 API 設定散落多處、互相矛盾

同一個「claude」模型，三個地方三種定義：
- `multi_ai_discuss.py MODELS`：`nvidia/nemotron-3-ultra-550b-a55b:free`（自稱 claude，實際是 nemotron！）
- `auto_develop.py`：預設 `nvidia/nemotron-3-ultra-550b-a55b:free`
- README：宣稱 `claude-3-5-sonnet-20241022`（已停用模型）

**這是嚴重的命名欺騙**：`MODELS` 列表叫 claude/gemini/deepseek/grok，但 model_id 全是別的模型。
`multi_ai_discuss.py --list-models` 顯示「claude ✅」會誤導使用者以為真的在用 Claude。

**建議**：
- 建立**單一模型設定檔**（`config/models.yaml` 或 `.env`），所有模組共用
- 移除已停用/不存在的模型 ID，名稱與實際模型一致
- `--list-models` 直接讀設定檔

### 🟠 P1：spec_auto_merge.py 生成「假內容」

`spec_auto_merge.py` 的 `05-merge-review.md` 對照表是**寫死的範例文字**：
```python
review_content += "| **錯誤處理** | Exception 繼承 | 錯誤碼工程化 | ... | ✅ 採用 DeepSeek |"
```
這些決策不是從模型輸出分析出來的，是硬編碼的假資料 → 會誤導人工決策。

**建議**：從模型輸出實際提取章節做對照，至少標註「範例，需人工確認」，或直接刪除假對照表只保留摘錄。

### 🟠 P2：run_tests 在「檢查失敗」時不回復任務狀態

`process_task` 第 1 步把任務設為 `in-progress`，若中途失敗（模型呼叫失敗/測試失敗），
`_record_failure` 會改回 pending（加 fail_count）✅，但 **git commit 失敗、diff 應用失敗路徑 OK**。
但 **`run_tests` 失敗後沒有把工作目錄還原**（git checkout）→ 失敗的程式碼殘留在工作目錄，
下次重試時 `git apply` 可能因檔案已被污染而失敗。

**建議**：測試失敗時先 `git checkout -- .`（或 stash）還原，再記錄失敗。

### 🟡 P3：apply_feedback.py 的 mark_as_done 有 bug

```python
text.replace(f"### Feedback #{fb['id']}", f"### Feedback #{fb['id']}")  # 替換前後一模一樣，無作用
```
這行是 no-op。狀態更新依賴下一行 `- **狀態**: [ ] 未處理` 的替換，但若模板狀態文字不同則無法標記完成。

**建議**：直接以 fb_id 區塊為單位重寫狀態行。

### 🟡 P3：setup_daemon.py 用 `sys.executable` 寫死 Python 路徑

launchd plist 中 `ProgramArguments` 使用 `sys.executable`（可能是 venv 或 pyenv 路徑），
若該 Python 環境被刪除/更新，服務開機即失敗。建議記錄實際路徑並驗證存在，或改用專案 venv。

### 🟡 P3：gen_mermaid.py 是「假生成器」

`generate_architecture_mermaid()` 回傳**寫死的圖**，`--project` 參數完全沒用到。
宣稱「自動掃描專案結構」，實際無掃描。建議：真的掃描（如 `index_knowledge` 的方式）或改名為 `mermaid_demo.py`。

## 五、流程問題

### 現有閉環（好的部分）
```
規格多AI諮詢 → 決策模板 → 任務檔 → auto_develop 實作 → 驗證 → commit → README 同步
     ↑                                                                    │
     └────────────── 反饋探勘 (extract_feedback) ← 對話紀錄 ────────────────┘
```

### 缺點
1. **無人工確認閘門**：auto_develop 完成後直接 commit，無 human-in-the-loop。建議：`git commit` 前若 diff 大於閾值（如 500 行），暫停等待確認；或產出 PR-style 摘要待審。
2. **失敗路徑不還原**（P2）
3. **文件同步斷裂**：`telegram_bot.py` 已刪除，但 README / currect_status / twin CLI 仍宣稱存在 → 需要一次「文件與現況對齊」任務
4. **blocked 任務無處理機制**：T006/T008 blocked 後沒有「人工 review → 拆分小任務 → 重試」的流程。建議 block 時自動生成 `T0XX-review.md` 記錄失敗原因與建議拆分方式

## 六、使用簡易度

### ✅ 好的
- `./twin` 一站入口，help 完整
- `./twin auto --once` 一鍵自動開發
- 任務檔格式統一（T001-xxx.md + YAML frontmatter）

### ⚠️ 待改進
1. **`./twin auto` 硬編碼 digital-twin**，無法指定其他專案（`auto_develop.py` 支援 `--project`，但 CLI 沒暴露）
2. `spec_auto_merge.py` 假資料會誤導（P1）
3. `--list-models` 顯示的模型名稱與實際不符（P1）
4. 錯誤訊息大多有 emoji 與中文，閱讀體驗好 ✅；但 `run_tests` 失敗輸出 2000 字截斷，缺少「哪個檢查失敗」的摘要行
5. **任務範本缺「依賴/相依任務」欄位**：T006 依賴 Redis 環境、T008 依賴討論決策，無法表達任務間依賴 → 建議 frontmatter 加 `depends_on`，auto_develop 依賴未完成時跳過

## 八、結論

**優點**：模組化切分清楚、統一 CLI 體驗佳、自動化閉環概念完整、diff 解析/修復機制設計用心、失敗計數與 blocked 保護機制有效（T006/T008 確實被擋下）。

**核心風險**：自動開發引擎的驗證閘門目前是「假閘門」（無測試 + pyright 掃空 + 333 ruff 錯誤），
而文件宣稱的能力（telegram_bot）與實際嚴重脫節。**在修復 P0/P1 之前，`./twin auto` 不宜直接投入使用**。

**建議優先序**：T011（設定統一）→ T012/T013/T014（引擎穩定性）→ T015（文件對齊）→ 其餘。
